# Mac アプリ・ウィジェット試作

SwiftUI の Mac アプリで Codex / Claude の残量と詳細を確認し、WidgetKit の中サイズウィジェットに短期・週次の4本の残量バーを表示する。macOS 14 以上、Xcode、Node.js 20 以上が必要。Node.js は同梱しない。

## 起動と署名

1. `TokenWatcher.xcodeproj` を Xcode で開く。
2. Git 管理外の `macos/Signing.local.xcconfig` に署名 Team ID を設定し、`TokenWatcher` と `TokenWatcherWidget` の両ターゲットで同じ Team が適用されていることを確認する。
3. Scheme `TokenWatcher` を選び、My Mac で実行する。
4. 通知センターの「ウィジェットを編集」から「TokenWatcher 残量」を追加する。

App Group は `$(DEVELOPMENT_TEAM).TokenWatcher`。両ターゲットの entitlement と Info.plist に同じ値を設定する。署名 Team は `Config.xcconfig` が読み込む Git 管理外の `macos/Signing.local.xcconfig` で指定する。ローカル設定の例:

```xcconfig
DEVELOPMENT_TEAM = YOUR_TEAM_ID
```

Team ID は実際の値に置き換える。必要な場合は、両ターゲットの Bundle Identifier も自身のものに変更する。Mac アプリは外部 CLI を実行するため App Sandbox を使わず、ウィジェットは App Sandbox を使う。配布・公証・App Store 対応は今回の対象外。

Xcode の「Signing & Capabilities」で Team を選び直すと、`project.pbxproj` に Team ID が直接保存される場合がある。個人の Team ID はローカル設定だけで管理し、コミット前に共有プロジェクトへの保存を確認する。

### `~/Applications` への配置

署名付きで動作を確認した後、TokenWatcher を終了する。Xcode の `Products → TokenWatcher.app` を右クリックし、`Show in Finder` でビルド済みアプリを表示する。`.app` 全体を `~/Applications` にコピーし、コピー先から起動する。ウィジェットと取得用 JavaScript もコピーされる。Node.js 本体は別途インストールしたものを使用する。

更新時はアプリを終了して再ビルドし、コピー先を置き換える。同じ Bundle Identifier / Team / App Group の場合、既存の設定・共有データを引き継ぐ。Xcode から起動したアプリとコピー先を同時に動かすと、取得・通知が重複する場合がある。

初回起動後、macOS がウィジェットを登録する。署名や App Group が未設定の場合は、共有できない理由を画面に表示する。アプリ内の情報取得は利用できる。通知センターへの追加・共有は、署名を設定して確認する。

### 「App Group を利用できません」と表示される場合

Team ID が未設定の場合、共有 ID は `.TokenWatcher` となる。macOS の一般的なプライバシー権限を追加しても、この設定は補われない。ローカル設定で両ターゲットに同じ署名 Team を指定し、共有 ID が実際の `<Team ID>.TokenWatcher` になった署名付きビルドで、アプリを再起動する。`CODE_SIGNING_ALLOWED=NO` のビルドは、Team ID が設定済みでも共有動作の確認には使わない。

必要な設定を用途別に分ける:

- ウィジェット共有: 同じ署名 Team / App Group。既存の Team ID 形式の設定を使い、片方だけ別のグループを追加しない。
- Codex 取得: `codex login` 済みの状態と正しい実行パス。
- Claude API 取得: ターミナル版 Claude Code のログイン状態と、必要に応じて表示されるキーチェーンアクセス許可。`statusline` はキャッシュだけを使う。
- Mac 通知: TokenWatcher の通知許可。通知センター方式と通知条件を有効にして保存すると許可を要求する。

初回は「情報取得を開始」で確認して開始する。開始した選択を保存し、次回起動から自動で取得する。App Group の警告はウィジェットへの共有に関するもので、アプリ内での利用量取得とは別の設定。

## 情報取得

起動時は App Group の最後の実データを復元する。保存値がない場合は「—」、300秒以上古い場合やリセット時刻を過ぎた場合は「更新待ち」を表示する。以前のサンプル値・破損 JSON は実データとして使わない。保存値の復元だけでは通知せず、新しい取得値が届く前に空値で上書きしない。

初回は実 API・キーチェーンへアクセスせず、メイン画面の「情報取得を開始」で確認して開始する。開始した選択を保存し、以後はアプリ起動時に自動取得する。旧設定で実データ取得を開始済みの場合も引き継ぐ。取得開始は画面の表示に依存せず、アプリ終了で停止する。認証情報自体は保存しない。通常画面のサンプル表示と「サンプルに戻す」は廃止し、サンプルはプレビュー・テストだけに残す。

設定の「取得」で Node.js の絶対パス、Codex の実行パス、取得間隔、待機時間、Claude の取得元を設定する。既定の Node.js パスは `/opt/homebrew/bin/node`。存在しない場合は `/usr/local/bin/node` を確認する。Codex は `codex` が既定で、PATH には Node.js のディレクトリ、`~/.local/bin`、Homebrew の標準ディレクトリを含める。

設定の「一般」で「メニューバーにアイコンを表示」をオフにして保存すると、メニューバーのアイコンを非表示にできる。設定は再起動後も保持する。Dock のアイコンやウィジェット全体のクリックでメイン画面を開く。ウィンドウを閉じても取得・通知は続き、「TokenWatcher → TokenWatcher を終了」または Command-Q で終了する。

- Codex: 既存ログイン状態を使う `codex app-server`。再試行は既存 CLI と同じ10秒・20秒・30秒。失敗後も常駐アプリは次の取得機会に再接続する。
- Claude `auto`: 利用量 API、失敗時は既存キャッシュ。最後の成功値があれば保持する。
- Claude `api`: 利用量 API のみ。失敗時は最後の成功値を保持する。
- Claude `statusline`: 既存キャッシュだけを読む。キーチェーン・API は使わない。

実データ取得の `auto` / `api` は、既存 CLI と同じキーチェーンの OAuth トークンを API 呼び出しに使う。トークンの表示・保存・更新は行わない。API の429応答で待機時間が指定された場合は、手動更新でもその時間を守る。同じブリッジ内では Codex の取得設定や Claude の取得元を変更しても待機期限を保持する。キャッシュのみの取得では API を呼ばず、API 取得へ戻した際に期限が残っていれば引き続き待機する。

429 の待機期限は API の `Retry-After` が指定した時間だけで計算し、取得間隔を追加の最低待機時間にはしない。期限後の定期取得・手動更新で再開する。通常の定期取得間隔は変更しない。

取得は既定180秒ごと。スリープ復帰時と「更新」でも取得する。サービスごとに取得の重複を抑え、一方が失敗しても他方は継続する。ウィジェット描画は OS が管理するため、180秒以内の反映は保証しない。

共有データは App Group 内の `usage-v1.json` に原子的に保存する。取得値、取得日時、取得状態のみで、認証情報は含まない。300秒以上古い値やリセット時刻を過ぎた値は「更新待ち」と表示し、残量を推測で回復させない。

### 詳細ログ

メイン画面の「詳細ログ」、取得エラー横の「詳細ログ」、またはメニューバーの「詳細ログを開く」で、取得成功・失敗・待機の記録を確認できる。「コピー」で一覧をコピーする。アプリ起動中の直近100件をメモリに保持し、取得が回復しても直前のエラーは残す。ログはファイルや App Group に保存せず、アプリ終了で消える。

Claude はキーチェーン読み取り失敗・タイムアウト、認証情報の欠落・期限切れ、API 通信失敗・HTTP ステータス・応答形式の異常を区別する。分かる範囲でシステムエラーコード、API の待機指定、手動更新を再開できる時刻、次の自動取得予定を表示する。時刻は目安で、スリープや処理時間により遅れる。Codex は起動失敗・タイムアウト・認証・終了など、識別できる分類を表示する。取得プロセス自体の停止も記録する。

認証情報、API 応答本文、生の例外メッセージ、標準エラー、環境変数はログに含めない。安全に分類できない場合は「安全に表示できる詳細情報はない」と表示する。既存の取得間隔・リトライ・通知の動作は変更しない。

## 通知設定

アプリの「設定」で Codex / Claude 別に保存する。初期状態は通知条件すべて無効、除外なし、通知方式はポップアップ。

| CLI オプション | GUI |
|---|---|
| `--notify-method` | 表示方法: ポップアップ / Mac 通知センター |
| `--notify-below` | 指定残量以下で通知: 0〜100％ |
| `--notify-every` | 一定割合減るごとに通知: 1〜99％ |
| `--notify-api-error` | 情報取得エラーを通知 |
| `--notify-exclude` | 複数の通知除外パターン |

除外は表示名と期間への部分一致で、大文字・小文字を区別しない。通知から除外しても、ウィジェットと詳細画面には表示する。モデル別制限など、ウィジェットに載らない制限も通知対象となる。

閾値到達・リセット後の回復・連続エラーの重複抑制は既存処理を再利用する。古い取得値から残量通知は出さない。閾値・刻み幅・除外の変更は現在値を新しい基準とし、変更だけでは通知しない。通知方法だけの変更は判定履歴を保つ。取得エラー通知の途中有効化も、それだけでは継続中のエラーを通知しない。

ポップアップはメイン画面の最小化中やアプリが非アクティブな状態でも前面に表示し、「閉じる」まで残る。情報取得は続ける。通知センター方式は TokenWatcher アプリの通知許可を要求する。macOS の「システム設定 → 通知」で許可・表示スタイルを設定できる。

CLI の引数は変更せず、GUI 設定とは独立する。CLI の起動引数は自動で取り込まない。CLI とアプリの両方で通知監視を有効にすると二重通知になる場合がある。

## テストとビルド

リポジトリのルートで実行する。すべてモック・サンプルを使い、実 API・キーチェーンには接続しない。

```sh
node --test
sh macos/test-models.sh
sh macos/test-scenes.sh
sh macos/render-preview.sh
xcodebuild -project macos/TokenWatcher.xcodeproj -scheme TokenWatcher \
  -configuration Debug -derivedDataPath .build/xcode CODE_SIGNING_ALLOWED=NO build
```

署名なしのビルドはコンパイル確認用。通知センターへの登録・App Group 共有・通知許可の確認は、署名を設定したビルドで行う。Swift のモデルチェックと Xcode の生成物は `.build` に保存する。

`render-preview.sh` は通常・低残量・ダーク表示・更新待ち・未取得の5種類を `.build/previews` に PNG として描画する。通知センター自体のスクリーンショットではなく、共通 SwiftUI ビューの表示チェック。

`test-scenes.sh` は別の識別子の検証用アプリを起動し、初回のサンプル廃止・前回値復元、Dock アイコンと同梱画像の一致、メニューバーの表示切り替え、Dock と URL のイベントによるメイン画面の再表示、最小化・非アクティブ中のポップアップ表示と閉じる操作、正常終了を確認する。Node.js ブリッジ・App Group・URL スキーム登録を含めず、認証情報・実データ・通常アプリの共有データは扱わない。画面更新中の状態変更の警告も検出する。ログは `.build/scene-tests/runtime.log` に保存する。

常駐ブリッジは `dist/widget-bridge.mjs`。アプリに同梱される既存 Node.js モジュールを読み、標準入出力の NDJSON で通信する。入力は `configure`（`config`）、`refresh`（任意の `service`）、`stop`。出力は `configured`、`snapshot`、`error`、`notification`、`diagnostic`、`protocolError`。`diagnostic` は待機指定による更新見送りなど、詳細ログ用の状態を伝える。通知要求はアプリが表示し、ブリッジ自身は通知ウィンドウを起動しない。標準エラーや未加工の上流応答を共有ファイルに保存しない。

実機確認では、通知センターへの追加、クリックによるアプリ表示、両通知方式、取得中の終了、スリープ復帰、ライト／ダーク、取得失敗時の前回値保持を確認する。
